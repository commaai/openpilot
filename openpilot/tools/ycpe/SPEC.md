# YCPE v1 spec

One static web app (vanilla JS ES modules, no build step, Chrome first) that replaces connect's route viewer,
useradmin's user-facing pages, cabana, jotpluggler and PlotJuggler. Data comes only from the comma API and blob
storage (or local files); there is no new backend. It must load rlog-only routes several hours long, and the
main thread may never drop a frame.

## Non-negotiables

- **Frame budget.** Main-thread work stays at 4 ms or less per frame, and nothing on the main thread is O(samples).
  Fetching, decompressing, parsing, migrating, decoding DBCs, searching and decimating all run in workers.
  The main thread only draws pixels and DOM.
- **Perf HUD.** The top bar always shows FPS, render ms (p50/max over the last second) and dropped frames.
  Clicking it opens the perf panel: a frame-time chart, long-animation-frame attributions, worker queue,
  load throughput, and memory by store tier. Every pane renders through the shared frame scheduler, so the
  HUD attributes time per pane.
- **One store, one namespace, one clock.** Every series has a path (`/carState/vEgo`, `/can/0/0x1a4`,
  `/dbc/0/GAS/PEDAL`, `/custom/name`). Every pane reads through the store API and follows the shared playhead
  and x-range. Views are layouts of panes, never separate apps.
- **Line budget.** At most 15k LOC hand-written (generated schema excluded). Every module has one job.

## Architecture

```
app.js           router, top bar (logo · omnibox · device › route breadcrumb · view tabs · perf HUD), auth
perf.js          frame scheduler (all rendering goes through it) + HUD + perf panel
api.js           comma API + athena RPC, memoized reads
data/
  codec/         zstd+bz2 wasm (104 KB) + build.sh, pinned sources
  schema.json    generated by gen_schema.py from cereal (Event = structs[0])
  capnp.js       schema-driven reader: every scalar → per-service columns (enum names, interned text,
                 lists ≤16 split per index, unions, groups, defaults, far pointers)
  worker.js      segment pipeline: fetch/OPFS → decompress → read → migrate → CAN index → compact → transfer
  loader.js      main-side segment scheduler: worker pool, playhead-out priority, OPFS cache, progress
  store.js       columns by segment, min/max pyramids, range queries, memory budget + column eviction
  migrate.js     column-level port of process_replay/migration.py
  can.js         per-message CAN frame store + bit-flip/byte-change summaries
  dbc.js         DBC parse + serialize (port of cabana dbcfile.cc, round-trip exact) + signal decode
panes/           one file per pane, each with the same small interface (below)
views/           layouts: drive (connect), plot (jotpluggler/plotjuggler), can (cabana), custom layouts
pages/           home/devices, device (routes, users, logs), route shell
harness/         QA: scenarios, perf gate, screenshot contact sheet, reference comparisons
```

**Pane contract.** `pane = create(ctx, state)` returns `{el, render(frame), resize(), dispose(), save()}`.
`ctx` is `{store, clock, route, layout, perf}`. `render` is called only when invalidated, and is timed by
perf.js. `save()` returns JSON for layouts.

**Clock.** `{t, playing, rate, loop, range: [t0, t1]}` plus subscriptions. The video is a follower
(and a leader when it plays), and the x-range is independent of the playhead, as in jotpluggler.

**Store tiers for hours-long routes.** On the demo route, 39 MB raw per segment currently parses to 6.7 MB
of columns; the target after sparse columns and narrowing is about 2.5 MB:

1. Compressed rlogs in OPFS. A revisit makes zero requests.
2. Columns for every segment, resident under a memory budget (about 1.5 GB by default). Columns that are
   plotted or in use are pinned.
3. Eviction is per column, not per segment. When an evicted column is requested again, its segments
   re-parse from OPFS at about 150 ms per segment per worker.
4. Min/max pyramids for pinned columns, so zoomed-out views of 10 hours cost O(pixels).

**Testing long routes.** `?repeat=N` on the demo route tiles its 16 segments N times with shifted
timestamps.

## v1 feature set (the parity checklists are the acceptance spec)

### Route browser (connect + useradmin, user-facing only)
- [ ] Sign in (Google/GitHub/Apple), sign out, and a JWT paste for developers. Public routes work signed out.
- [ ] Omnibox accepts a dongle id, a route name, a connect URL, a useradmin URL or a `cabana` route string.
- [ ] Device list (alias, online dot, last seen, version) and device rename.
- [ ] Device page: location map; route list (date, duration, distance, engaged %, thumbnails, paging back
      in time); preserved routes; device users (list, add, remove); boot logs and crash logs (opened in
      our own log viewer).
- [ ] Route page (the **drive view**): qcamera video, engagement/alert/override timeline with thumbnails,
      map with the playhead marker, route info (car, version, branch, segments), public and preserved
      toggles, copy link and share.
- [ ] Files: a per-segment table of every file kind with download, upload status for each file, and
      **request upload** (athena `uploadFilesToUrls` via `upload_urls`). Also "upload all rlogs" or all files
      of a kind, the upload queue with cancel, and an offline notice when the device can't be reached.
- [ ] Moving from any route view into plot or CAN keeps the same route, time and selection. Bookmarks
      (user flags) appear on the timeline.

### Plotting (jotpluggler + PlotJuggler)
- [ ] Series browser: a tree of every path, filter/regex, values at the playhead, hiding of deprecated
      fields, multi-select, and drag onto plots. Units and enum types appear on hover.
- [ ] Time plots in tabs with recursive horizontal/vertical splits, draggable dividers, and pane
      add/close/swap.
- [ ] Shared x-range with zoom (wheel, box, axis drag), pan, auto-fit, y-lock/limits, linked or unlinked
      axes, and undo/redo of view and layout.
- [ ] A tracker line with a legend showing values at the cursor. The playhead and the cursor can differ.
- [ ] Curve styles (line, steps, dots, line+dots, sticks), color picking, and per-curve scale, offset and
      time shift.
- [ ] Enums and text drawn as state blocks with labels; bools and integers drawn as steps;
      `valid=false` spans marked.
- [ ] XY plots, with the playhead shown as a moving point.
- [ ] Transforms: derivative, integral, moving average, moving RMS/variance, abs, first difference,
      outlier removal and FFT; also quaternion → RPY.
- [ ] Statistics over the visible range: min, max, mean, std, count, rate.
- [ ] Custom series in a **JavaScript** code console that runs in a worker. It takes any number of
      inputs, resamples them to the first one, keeps a persistent globals block, ships the jotpluggler
      templates, and is saved in the layout.
- [ ] Layouts: our own JSON (with autosave and a URL share), importing all 17 jotpluggler layout JSONs
      and all 14 PlotJuggler XMLs (Lua snippets translated to JS where it's mechanical, otherwise flagged),
      and a layout picker.
- [ ] Export: CSV of the selected series over a range, and PNG of a plot.
- [ ] Panes: camera (road, wide, driver, qcam), map (GPS trace colored by engagement), logs (logMessage,
      errLogMessage, alerts/onroadEvents, journal; filter by level, source and text; click to seek),
      message inspector (the full decoded message of any service at the playhead, as a tree), and
      initData/carParams viewers.
- [ ] Playback: play/pause, rate 0.01–5×, step, loop range, keyboard shortcuts, and a timeline scrubber
      with engagement and alert overlays.

### CAN (cabana)
- [ ] Messages table: bus, address, name, count, frequency, live bytes with change highlighting,
      filters (any column, by bus), suppress-highlighted and suppress-defined, and sorting.
- [ ] Binary view: bit grid with a flip heatmap (live or over the range), signal overlays with overlap
      colors, drag to create signals (all four drag directions), resizing signal edges, and hover info.
- [ ] Signal editor: name, size, endianness, signed, factor, offset, min, max, unit, comment, value
      descriptions, receivers and multiplexing (mux/muxed). Signal list with sparklines.
- [ ] Message editor: name, size, transmitter node, comment. Undo/redo for every DBC edit.
- [ ] DBC: auto-load from the fingerprint, choose from opendbc (bundled list), open a file, paste,
      save to file (File System Access writes back when permitted), copy to clipboard, a DBC per bus,
      and an exact round-trip of unknown sections.
- [ ] Charts: signals from any DBC message (they're also series in the plot view), tabs, merging charts by
      drag, line/step/scatter, value tips, and column layouts.
- [ ] History log: decoded or hex, filter by signal comparisons, and click to seek.
- [ ] Tools: find similar bits, find signal (value or changes over a range), route info (segments), and
      CSV export of raw and decoded data.
- [ ] Video plus a timeline with alerts and thumbnails, shared with the other views.

### Data correctness
- [ ] Every cereal field is readable from every era of log (bz2, zst, raw; old schemas through deprecated
      fields).
- [ ] All 19 migrations from migration.py run at column level and diff clean against Python
      `migrate_all` on reference logs from several eras and brands (process_replay reference logs on
      openpilotci).
- [ ] The reader agrees value-for-value with pycapnp on a field-by-field dump of reference segments
      (a scripted check that runs in CI).
- [ ] Full-res video: HEVC fcamera/ecamera/dcamera through WebCodecs, with frame-accurate seek using
      encodeIdx, plus qcamera through HLS.
- [ ] Local data: drop a route folder or log files onto the page, or open them with the File System
      Access API.

Out of scope for v1: prime/billing, pairing, clips, body teleop, livestream, WebUSB panda, live device
streams, and anything internal (god mode).

## How the work is organized

**Shell and layout: Adeeb + root, interactive.** This covers:
- the top bar (logo, omnibox, device › route breadcrumb, view tabs, perf HUD)
- perf.js, the frame scheduler every pane renders through
- the layout engine (tabs, recursive splits, drag/drop of panes and series, save/restore, URL state)
- the clock and playback bar
- the views (drive, plot, can) as layouts
- global keyboard handling, theme and overall feel

Root owns `app.js`, `perf.js`, `clock.js`, `layout.js`, `views/`, `style.css` and `index.html`.

**Deep tracks: one subagent each, running in parallel in their own git worktrees.** Each owns its files
outright, works against the contracts below, and develops in a standalone dev page (`dev/<track>.html`)
until its panes are mounted in the shell. Root's job is to coordinate, line-review every diff, integrate
onto branch `ycpe`, broadcast "merge ycpe" when a contract-relevant change lands, run the harness and the
polish loop, and keep everyone moving.

| # | Track | Owns | First milestone |
|---|---|---|---|
| 1 | Log pipeline perf | data/capnp.js, codec/, worker.js, loader.js, store.js | store v0 behind the contract, delivered as soon as possible (it unblocks 4 and 6). Then make it fast: sparse/narrow columns, worker pool, OPFS cache, playhead-out priority, memory budget + column eviction, pyramids, `?repeat=N` benchmark with numbers. |
| 2 | Correctness + migrations + logs/inspector | data/migrate.js, harness/parity/, panes/logs.js, panes/inspector.js | A parity dump comparing pycapnp and capnp.js on every field of reference segments from several eras. Reader bugs go to track 1 as failing tests. |
| 3 | Cabana | data/can.js (the worker-side CAN extraction hook), data/dbc.js, panes/can/*, dev/can.html | DBC parse/serialize round-trip against cabana's test suite. Then the messages table, binary view, signal editing, history, find tools and charts. |
| 4 | Plotting | panes/plot/*, data/transforms.js, data/custom.js, layouts/import.js | The time-plot pane with decimation, tracker, state blocks and styles. Then XY, transforms, stats, the JS console, jotpluggler/PlotJuggler layout import and export. |
| 5 | Video | panes/camera.js, data/video/* | qcamera HLS synced to the clock, then frame-accurate HEVC through WebCodecs for f/e/d cameras, plus thumbnails. |
| 6 | Route browser + athena + map | pages/*, panes/map.js, panes/timeline.js, api.js | Devices, routes, files, uploads, users, boot/crash logs, and the drive-view panes. |
| 7 | QA harness | harness/ (except parity/) | The scenario runner, perf gate, UI lint, report.html with contact sheet, and reference screenshots of native cabana/jotpluggler and connect.comma.ai. |

**Rules for every track:**
- Never touch files owned by another track; send requests to root instead.
- Never touch native tools or anything outside `openpilot/tools/ycpe/`.
- Make no mutating API calls against real devices or routes: no preserve/public toggles, no uploads.
  Exercise those with request interception.
- Commits are small and lowercase (`ycpe: ...`) with no body.
- Every milestone reports measured numbers and screenshots.

## Contracts (changed only by root)

```js
// clock.js: one per route workspace, all times in route seconds
clock = {t, playing, rate, loop: [a, b] | null, duration, range: [t0, t1],   // range = visible x-range
         seek(t), play(), pause(), toggle(), setRate(r), setLoop(l), setRange(t0, t1), setDuration(d),
         on(event, fn) /* "t" | "range" | "play"; returns an unsubscribe */}

// perf.js: every pane renders through the scheduler; never call requestAnimationFrame directly
perf.invalidate(pane)          // pane.render(frame) runs once on the next frame, timed under pane.name
perf.tick(fn)                  // fn(frame) every frame until the returned unsubscribe is called
perf.measure(name, fn)         // ad-hoc timed section
perf.mark(name, value)         // a counter in the perf panel (bytes, queue length, MB/s)
// window.__perf = {frames: [{t, n, interval, work, panes: {name: ms}}] (last 600), longFrames, marks, drops}

// pane modules: export function create(ctx, state); registered in panes.js (type -> file)
ctx = {route,                  // the API route object (fullname, start_time_utc_millis, url, maxqlog, ...)
       clock, perf, theme,     // theme.color("--fg"), theme.on(fn); redraw canvases on theme change
       store,                  // getter: touching it starts loading rlogs. Panes that work without logs
       peekStore(), onStore(fn),//   (qcamera, map from coords.json) use peekStore()/onStore() instead
       layout,                 // the Layout; layout.replaceSelf(pane.el, {pane: type, state})
       openRoute(name)}        // switch route, keeping the view
pane = {name, el, title?, render(frame), resize(w, h), dispose(), save() /* JSON state for layouts */}
// el is absolutely positioned to fill the pane body; panes must not scroll the page

// store.js: main thread; never O(samples) per frame
store.route                    // {name, t0 (mono s), duration, segments: [{n, t0, t1, status}]}
store.on(event, fn)            // "segment" (n) | "paths" | "progress"
store.paths()                  // [{path, type, names?}], type: f32 f64 b e t (enum names for e)
store.series(path)             // {path, type, names, chunks: [{t: Float64Array (route s), v, i?}], version}
                               // chunk.i: sparse index into the service times, if present
store.decimate(path, t0, t1, n)// {t, min, max} with n buckets (min/max pyramid); exact samples if few
store.valueAt(path, t)         // last value at or before t
store.message(service, t)      // the full decoded message at t (for the inspector), async
store.focus(t)                 // load outward from t
store.can                      // owned by track 3: messages(), frames(bus, addr, t0, t1), ...
```

Pane registry (panes.js): routes→panes/routes.js (root), camera→panes/camera.js (state {camera: qcamera|fcamera|ecamera|dcamera}),
map→panes/map.js, info→panes/routeinfo.js (route info + files + uploads), plot→panes/plot/plot.js, xy→panes/plot/xy.js,
browser→panes/browser.js, logs→panes/logs.js, inspector→panes/inspector.js, can-messages|can-binary|can-signals|can-history|can-charts
→panes/can/{messages,binary,signals,history,charts}.js. Series drag-and-drop between panes uses DataTransfer type
`application/x-ycpe-paths` with a JSON array of paths.

## Quality harness (track 7)

`harness/run.py` uses Playwright with real Chrome and records everything into `harness/out/<run>/report.html`:

1. **Scenarios as data.** Each is `{url, viewport, steps: [click/drag/wheel/key/wait], shots}`: cold and
   warm load, a ×10 route, rapid zoom/pan, scrubbing, 5× playback, switching views, dragging 20 series in,
   creating a DBC signal, every dialog, a mobile drive view, and error and empty states.
2. **Perf gate.** Pass/fail comes from long-animation-frame entries plus the perf.js per-pane timings.
   - A scenario fails on any frame over budget, or on any frame over 50 ms at 4× CPU throttling.
   - The report charts frame time against the previous run.
3. **UI lint:**
   - console errors, failed requests and unhandled rejections
   - viewport overflow, clipped text, overlapping controls and hit targets under 24 px
   - layout shift
4. **Contact sheet:** every screenshot from every scenario on one page, plus per-pane crops.
5. **Reference comparisons:**
   - Native cabana and jotpluggler (`--output` screenshots on Xvfb) and connect.comma.ai, side by side
     with our view at the same route and time.
   - Plotted values must equal jotpluggler's at matching times.
6. **Golden screenshots** with a perceptual diff.

## Integration cadence

1. Each track works on branch `ycpe-<track>` in its own worktree.
2. When a milestone is ready, root reviews it line by line, merges it into `ycpe`, and tells the other
   tracks whether to merge.
3. Polish loop, once the shell can mount the panes:
   1. Run the harness.
   2. Critic agents, each with a single lens (visual, interaction, parity, perf, copy), file numbered
      findings.
   3. The owning track fixes them.
   4. Root reviews every fix and re-runs.

   It stops when a round turns up nothing new.

## Spike status

- codec.wasm is built: zstd decodes at 550 MB/s, byte-exact for zstd and bz2.
- gen_schema.py writes schema.json (95 KB, 261 structs, 68 enums).
- capnp.js reads a full demo segment in about 90 ms (on top of about 65 ms to decompress) into
  1,718 columns over 49 services, including enum names, text, per-index small lists and pandaStates.
- Next for the spike: sparse columns and float32 narrowing (6.7 MB → about 2.5 MB per segment),
  then the worker pool and the ×10 benchmark.
