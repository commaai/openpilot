# Narrow road 720p120 bench

`CAMERA_720P120=1` selects an experimental comma four / OS04C10 mode. The
default is unchanged. Wide road and cabin sensors are initialized to keep their
GPIOs configured, but are not started and allocate no ISP pipelines. Only the
narrow stream is published. This is a standalone camera/WebRTC experiment, not
a driving configuration; it does not run modeld or alter its frame cadence.

## Automatic startup with the normal manager

On the comma four, enable the persistent opt-in once:

```sh
touch /data/camera720p120
```

Then launch `./launch_openpilot.sh` normally or reboot. `launch_env.sh` reads
this marker and sets `CAMERA_720P120=1`. Normal onroad startup starts camerad,
one `stream_encoderd --stream` and webrtcd on port 5001. Going offroad stops
them normally. No manual `IsOffroad` override or separate bench runner is needed.
The manager mode has no one-hour bench timeout; the normal hardware/onroad
lifecycle applies. Do not run `scripts/camera120.py` alongside the manager.

Recording encoders/loggerd, driving models, driver monitoring and dependent
localization/planning processes are disabled in this mode. Panda, card, hardware
management and UI retain their normal lifecycle. For `brand=pinball` and
`notCar=true`, selfdrived and joystickd retain the existing control path and
200 ms joystick watchdog. Only the intentionally absent vision services and
driving calibration are excluded from pinball engagement checks. The narrow
camera, CAN, thermal and control checks remain. Other vehicle interfaces cannot
enable controls in this experimental mode.

To revert, remove `/data/camera720p120` and restart openpilot or reboot.
`CAMERA_720P120=0 ./launch_openpilot.sh` provides a one-launch override even if
the marker exists. Builds and source changes remain installed in either mode.

## Sensor configuration

The base sequence is the supplied OmniVision `OS04CR4DEV217_AE02.ovd` section
`DP_1280x720_Bin2_AHBIN_LINEAR_MIPI0728Mbps_240FPS_10BIT_FOURLANE`.
Only `6c` sensor writes are imported, with stream-on/off omitted. The FPGA/host
commands in the OVD are not sensor registers and must not be sent over I2C.

The experiment retains the vendor clocks and HTS=535, doubles VTS from 786 to
1572 for nominal 120 FPS, uses 1280x720 RAW10 with sensor-side binning, and
disables external FSIN synchronization. Panda remains untouched at 20 Hz.
The linear exposure maximum is VTS-8 (1564 lines), per the v2.07 datasheet.
Lens shading correction is disabled because its full-resolution calibration
does not match this crop. RAW10 black level is 64, matching vendor BLC target
register 0x4003=0x40; it is not the existing RAW12 pedestal divided by four.
The vendor sequence also omits openpilot's manual white balance. Apply the
existing OS04C10 gains to both register banks (0x5100–0x5105 and
0x5140–0x5145): B=0x067e, G=0x0400, R=0x08d6. Unity is 0x0400 per datasheet
section 5.7. Leaving the vendor defaults produces a green cast with the
existing color-correction matrix.

Readout time in camera metadata is an estimate from the vendor timing, not a
measured EOF. Verify color arrangement, black level, orientation, exposure,
actual FPS and CSI/ISP errors on hardware. The OVD enables a host REMOSAIC
option in multiple modes, so its presence alone does not establish a need for
a new remosaic algorithm. A color target test remains necessary.

## Build and run

Include the changes in `teleoprtc_repo` when copying the checkout. On comma four:

```sh
cd /data/openpilot
scons -j4 openpilot/system/camerad/camerad openpilot/system/loggerd/encoderd
# Stop the normal manager and its children, with the device parked/offroad.
python3 scripts/camera120.py --duration 60
```

Open `http://<comma-IP>:8000` on the same LAN and click Connect. The standalone
page explicitly requests Constrained Baseline profile Level 4.2. A receiver offering only
Level 3.1 is rejected, rather than being sent an incompatible stream. Browser
hardware decoding at this rate is device-dependent. The page reports decoded
FPS, display FPS, received bitrate, frame drops and packet loss; a 60 Hz display
can show fewer frames than the decoder receives.

The runner launches only camerad, `encoderd --stream`, and webrtcd. It reports
capture and encoded FPS, aborts on missing output, sustained frame loss/rate
failure, leaving offroad state or a CPU/GPU/DDR thermal reading of 85 C, and
stops automatically after the requested duration. Ctrl-C also stops the bench.
The default stream bitrate is 20 Mbps. Client quality settings select High=20,
Medium=10, and Low=5 Mbps; Auto adapts between these levels. `STREAM_BITRATE`
overrides the High target. Normal camera mode retains its existing bitrate levels.

The live encoder uses 120 FPS and H.264 Constrained Baseline Level 4.2, with a 30-frame GOP.
WebRTC queues encoded frames without conflation, waits for a keyframe after
a source gap, and derives 90 kHz RTP timestamps from capture SOF timestamps.
The normal recording encoderd is intentionally refused in this mode, avoiding
additional encoder load and incorrect assumptions about recorded frame rates.

## Recovery

No bootloader, kernel, Panda firmware or OTP is modified. For the standalone
runner, stop it and restart without the environment flag. For manager startup,
remove the opt-in marker described above and restart. If the camera driver is wedged, power-cycle
the device. The sensor register state is volatile.

## Local checks

```sh
python3 -m unittest openpilot.system.webrtc.tests.test_camera120 -v
```

These test 120-frame timestamp cadence, reference-frame loss recovery, camera
selection, default-mode behavior, and rejection of insufficient H.264 levels.
They do not establish hardware throughput or image quality.

## Device validation, 2026-09-13

Built camerad and the Qualcomm V4L2 encoder on a comma four and tested only
the narrow road camera. Capture and encoded output measured 120.26 FPS at
1280x720 without frame-ID gaps in the sampled windows. Chromium decoded
approximately 120 FPS over WebRTC at roughly 5 Mbps with no reported RTP packet
loss. The browser reported a few startup frame drops, then a stable count;
its 60 Hz presentation ran at about 60 FPS.

The initial RAW10 pedestal conversion was incorrect and was corrected to the
vendor target of 64. The corrected stream showed the room with working exposure
control (a sample was 514 exposure lines at 1x gain). Color/white-balance and
geometric calibration have not been retuned for this experimental mode.
The hottest sampled CPU/GPU/DDR temperature was about 45 C. These are bench
measurements, not validation for driving or for every browser/network.

Manager integration was built and started through `launch_openpilot.sh` on the
camera bench. Only the narrow VisionIPC stream was available; capture and
stream encoding both measured 120.26 FPS without frame-ID gaps over 12 seconds.
The native client decoded 119.53 FPS at the High target in a separate 15-second
run (9 local drops, 1 recovered decode error). All 12 manager, pinball-state and
camera-stream tests passed on the device. Physical pinball actuation was not
tested because the controller was not connected.

The native Pinball client advertises H.264 Level 4.2 and connects directly to
webrtcd on port 5001. From the parent Pinball checkout, run:

```sh
uv run client/viewer.py 192.168.60.187 --camera road --connect
```

A 30-second native transport test decoded 119.57 FPS with 20 dropped frames
and no decode errors. The full viewer submitted approximately 118 FPS in an
Xvfb/llvmpipe software-rendering test; it reported 103 dropped frames and one
decode error over the complete 35-second session and recovered. These are
separate runs, with different rendering and bitrate loads. Physical display
refresh still limits visible FPS. The client transport regression suite passed
24 tests, including normal 20 FPS compatibility with the higher receive level.
Only one viewer can receive at a time; a new connection replaces the old one.
